# 写作指南：如何把 pi 源码的核心价值写成好教程

> 本文是 `learning/` 全部教程文档的写作规范。动笔前先读一遍，写完后逐条对照检查。
> 风格基准：阮一峰《ES6 标准入门》。它是中文技术教程的典范，本指南提炼其写作逻辑，并针对"源码架构教程"（而非"语法教程"）做了适配。

## 一、我们在写什么

先明确定位，避免写歪：

- **不是 API 文档**——不追求覆盖每个函数每个参数，官方 README 已经干了这件事。
- **不是源码逐行注释**——读者不需要你复述代码，他自己会看。
- **是"核心价值"教程**——回答三个问题：这段设计**解决什么问题**、**怎么解决的**、**为什么这么解决**（而不是别的方案）。读完后读者应能把这些架构思想迁移到自己的项目里。

一句话检验标准：**如果删掉某一节，读者对 pi 架构的理解不受损，这一节就不该写。**

## 二、从阮一峰教程学到的六条核心手法

### 1. 论断先行，例证紧跟

阮氏每个知识点的展开有固定节奏，值得背下来：

```
一句话论断（新概念是什么/行为是什么）
    ↓
一段极简代码（10 行以内，能独立成立）
    ↓
"上面代码中，……"（指着代码解释，落到具体变量/行为上）
    ↓
推论或延伸（"这表明……"/"也就是说……"）
```

看原文的实际例子：

> ES6 新增了`let`命令，用来声明变量。它的用法类似于`var`，但是所声明的变量，只在`let`命令所在的代码块内有效。
>
> ```javascript
> {  let a = 10;  var b = 1; }
> a // ReferenceError
> b // 1
> ```
>
> 上面代码在代码块之中，分别用`let`和`var`声明了两个变量。……这表明，`let`声明的变量只在它所在的代码块有效。

注意顺序：**先给结论，再给证据，最后指着证据把结论重说一遍**。读者永远不会在看代码时不知道"我该看出什么"。

对应到源码教程：先说"这个模块的错误不走异常通道，而是编码成一条普通消息"，再贴那段 `stopReason: "error"` 的代码，再指着代码说"注意 catch 块里没有 rethrow，而是构造了一条 assistant 消息"。

### 2. 每段代码都有"上面代码中"式解读

这是阮氏教程最显著的排版特征：**代码块永远不裸奔**。每段代码后面必须有一段散文，以"上面代码中"或等价句式开头，把代码里的关键标识符点名说清。

反面典型（我们要避免的）：贴 50 行源码，前后各一句"核心逻辑如下"“就是这样”。读者被迫自己在 50 行里找重点。

正确做法：
- 源码先**裁剪**到只剩表达论点的 5~15 行，无关细节用 `...` 或注释省略
- 代码后立即解读："上面代码中，`emit` 返回 promise 且被 await，这意味着……"

### 3. 递进结构：用法 → 规则 → 陷阱 → 动机

看 let 一章的小节顺序：基本用法 → 不存在变量提升 → 暂时性死区 → 不允许重复声明 →（下一大节）**为什么需要块级作用域**。

这是一条精心设计的认知曲线：

1. **最普通的用法**先出场（让读者 30 秒内"会用"）
2. 然后是**行为规则**（边界在哪）
3. 然后是**反直觉的陷阱**（typeof 死区、隐蔽死区——认知升级）
4. 最后回头讲**设计动机**（"为什么需要"——此时读者已有足够上下文理解动机）

对应到源码教程的章节骨架：

1. **这个模块解决什么问题**（一段话，给场景不给术语）
2. **最小工作示例/主干流程**（读者先看到全貌怎么转）
3. **关键机制逐个深入**（每个机制独立小节，按依赖顺序排列）
4. **精妙细节与边界情况**（截断保护、并发时序……这是"暂时性死区"式的内容，最有价值）
5. **设计动机与取舍**（为什么不用方案 B；这个设计付出了什么代价）

### 4. 对比是最好的说明

阮氏讲 let 从头到尾在和 var 对比：同一段循环代码，var 版输出 10，let 版输出 6。**差异让特性变得可感**。

源码教程同样：讲 pi 的方案时，尽量给出"朴素方案"作对照——

- "如果启动时解析一次 API key（朴素方案），OAuth token 会在长工具执行期间过期；所以 pi 在每次 LLM 调用前才解析（实际方案）。"
- 表格对比也算：串行 vs 并行工具执行的三种事件顺序保证。

### 5. 预判读者的疑问，当场回答

原文有个典型段落：

> ……所以最后输出的是`6`。**你可能会问**，如果每一轮循环的变量`i`都是重新声明的，那它怎么知道上一轮循环的值？这是因为 JavaScript 引擎内部会……

写作时在每个论断后停一秒，问自己"读者此刻最可能问什么"，如果问题成立，**下一段就回答它**，不要留到章末 FAQ。

源码教程常见的该预判的疑问：
- "为什么不直接 XXX？"（设计取舍类）
- "那如果 YYY 会发生什么？"（边界情况类）
- "这个和刚才讲的 ZZZ 是什么关系？"（概念关联类）

### 6. 语言：短句、白描、术语中英对照

- **短句**。一句话一个意思。超过两行的句子拆掉。
- **白描**。不用"优雅""强大""巧妙"这类空洞赞美词直接下判断；把机制说清楚，读者自己会觉得巧妙。少量点睛处可以用"关键洞察是……"提示重点。
- **术语首次出现给中英对照**：暂时性死区（temporal dead zone，简称 TDZ）。源码教程同理：插话（steering）、压缩（compaction）、清单（transcript）。之后行文可以只用一种，但要一致。
- **"总之"收束**。一个复杂小节讲完，用一两句"总之……"把本质重说一遍。这是给读者的记忆锚点。

## 三、针对"源码教程"的额外规范

语法教程的对象是稳定的语言规范，源码教程的对象是一个具体仓库，有几条额外要求：

### 1. 永远给出源码坐标

每一节开头标注本节对应的源码位置；文中引用代码时给相对路径（必要时加行为特征而非行号，行号会漂移）：

```markdown
> 源码：`packages/agent/src/agent-loop.ts`（约 780 行）
```

读者随时能"跳进源码对照"，这是源码教程和语法教程的最大区别——**我们的教程是源码的导游图，不是替代品**。

### 2. 代码引用规则

- **裁剪重排优先于原样粘贴**。可以删掉错误处理、日志、类型体操，用 `// ...` 标记省略，但**不允许改写语义**——读者对照源码时不能产生"教程骗我"的感觉。
- 大段机制用**带注释的伪代码**呈现主干（10~25 行），再对个别关键真实片段精讲。
- 每段代码控制在一屏内（25 行以内）。超过就说明你还没找到重点。

### 3. 图表的使用时机

- **分层/依赖关系**：ASCII 框图（洋葱图、管道图）
- **流程/循环**：带缩进的伪代码或步骤列表，比流程图更容易维护
- **多方案对比/事件顺序**：表格
- 图表和代码一样不许裸奔，前后要有引导句和解读句

### 4. 每章末尾：动手验证

阮氏教程的读者可以打开控制台立刻验证任何论断。源码教程要主动制造这种可验证性——每章结尾给一个"动手实验"小节：

- 指出用什么跑（本项目：faux provider 不花钱、`tsx` 直接跑 TS 源码、`test/` 里现成的测试）
- 给出具体做什么、预期观察到什么
- 一个实验就好，宁精勿多

### 5. 章间衔接

- 每章开头一句话说明**本章在整个学习路线中的位置**（承接哪章、为哪章铺垫）
- 用到后续章节才展开的概念时，一句话简介 + "详见第 N 节"，不展开
- 目录文档（`learning/README.md`）维护全局阅读顺序

## 四、单章模板

```markdown
# NN · 章标题（点出主题的价值，不只是模块名）

> 源码：`packages/xxx/src/yyy.ts`
> 位置：本章承接第 N-1 节的 XXX，为第 N+1 节的 ZZZ 铺垫。

## 1. 它解决什么问题
（场景化描述痛点。朴素方案是什么、会遇到什么麻烦。一两段。）

## 2. 主干：它是怎么工作的
（最小示例或主流程伪代码。先让读者看到全貌。）

## 3~N. 关键机制（每个机制一节）
（论断 → 裁剪后的代码 → "上面代码中……"解读 → 推论。
 预判疑问当场回答。有对比给对比。）

## N+1. 精妙细节 / 边界情况
（最有含金量的部分：截断、并发、崩溃恢复……每个细节说清"不这么做会怎样"。）

## N+2. 设计动机与取舍
（为什么不用方案 B？这个设计的代价是什么？"总之"收束。）

## 动手实验
（一个可操作的验证步骤 + 预期现象。）
```

## 五、发布前检查清单

- [ ] 每个论断后面有代码或事实支撑，每段代码后面有"上面代码中"式解读
- [ ] 单段代码 ≤ 25 行，且做过裁剪
- [ ] 小节顺序是递进的：用法 → 规则 → 陷阱 → 动机
- [ ] 至少有一处"朴素方案 vs 实际方案"对比
- [ ] 术语首次出现有中英对照，全文用法一致
- [ ] 每节有源码坐标；章首有路线定位；章尾有动手实验
- [ ] 删除了所有空洞赞美词；复杂小节有"总之"收束
- [ ] 自问：删掉这一节，读者的架构理解受损吗？不受损就删
